# Diagrams: k3s job-search pipeline

Five diagrams for the laptop-hosted k3s pipeline, generated from one generator
(`tools/gen_mdj.py`) in two forms: StarUML 6 (`.mdj`, kept as legacy) and
PlantUML (`.puml`, the active, editable format, rendered inside IntelliJ). The
source of truth for the content is `docs/diagrams/facts.md` (live cluster
evidence, 2026-10-11), the Obsidian architecture note, and - for collection
field lists beyond the indexes - the Kotlin repos (`JobStateRepositoryImpl`,
`Recorder`, campaign-api entities).

`tools/gen_mdj.py` regenerates the `.mdj` files and the `plantuml/*.puml`
sources from the same specs, so the diagrams stay reproducible when `facts.md`
changes.

The older `export/*.svg` files are the StarUML renders of the legacy `.mdj`
copies; the `plantuml/export/*.svg` files are the active renders.

Open the live diagrams in IntelliJ with the PlantUML integration plugin. Just
open a `.puml` file; the plugin renders it in the PlantUML tool window, and its
code navigation jumps between diagram elements and source lines.

```
open -a "IntelliJ IDEA" plantuml/01-uml-deployment.puml plantuml/02-arch-job-pipeline.puml plantuml/03-mongo-data-model.puml plantuml/04-gcp-msrouter-providers.puml plantuml/05-wa-mcp-opencode.puml
```

## How the files were validated

Each `.puml` is rendered headlessly by the PlantUML engine bundled with the
plugin, so a clean render is a load test:

```
JAVA="/Applications/IntelliJ IDEA.app/Contents/jbr/Contents/Home/bin/java"
JAR="$HOME/Library/Application Support/JetBrains/IntelliJIdea2026.1/plugins/plantuml4idea/lib/plantuml-mit-1.2026.8.jar"
for f in plantuml/*.puml; do
  "$JAVA" -Djava.awt.headless=true -jar "$JAR" -charset UTF-8 -tsvg -pipe \
    < "$f" > "plantuml/export/$(basename "${f%.puml}").svg"
done
```

The committed `plantuml/export/*.svg` came from that command. Each SVG text is
grepped for the expected labels (node names, attribute rows, edge labels, note
text).

Plugin install: "PlantUML integration" (`plantuml4idea`, version
7.15.0-IJ2023.2, `since-build=232` with no upper bound) into IntelliJ 2026.1.
The `.mdj` copies were load-tested with the StarUML app the same way
(`StarUML image <f>.mdj -f svg -o ...`) when they were created. StarUML
(2026-10-12) and draw.io are uninstalled; the `.mdj` files stay committed as the
original format, and the PlantUML sources are the active, editable form.

## How the schema was learned

StarUML 6 has no view-bearing `.mdj` samples, so its schema was decoded from
the app bundle: `app.asar` -> `extensions/essential/uml/metamodel.json` and
`elements.js` (`UMLNodeView`, `UMLClassView`, `UMLNoteView`, `UMLDependencyView`
class definitions) plus the bundled `UMLMinimal.mdj` template. Empirical
findings (each confirmed by export-and-grep):

- View text is generated by the app from the model. Hand-written `subViews`,
  `nameCompartment` or `attributeCompartment` refs cause the app to drop the
  view entirely. Views therefore carry geometry only; the element carries the
  `name`, the `attributes`, or the note text.
- `UMLNoteView` never reads the model: multi-line note text belongs on the
  VIEW (`text`), not on the `UMLNote` element.
- An edge view needs distinct ids for its model element and its view; reusing
  one id suppresses the edge label.
- Edges are the one exception to the geometry-only rule: a relation view owns
  its three `EdgeLabelView` sub-views and the `nameLabel` / `stereotypeLabel`
  / `propertyLabel` refs; boxes never carry `subViews`.
- Class attribute rows are label views whose `text` lives on the row view, and
  the class element keeps attributes in its own `attributes` array.

Those findings are the complete set the generator relies on. The PlantUML
emitter reads the same model (names, attributes, note text, relations) and lets
PlantUML lay the graph out itself.

## Layout policy

Graphic text runs left to right, one label per line. In the `.mdj` form boxes
are sized from their longest line (about 6.3 px per character at Arial 12), so
nothing wraps or clips; each grid keeps at least one row of slack and box
overlap is checked at generation time. The `.puml` files use PlantUML's own
auto-layout, so box positions differ between the two forms while the text and
relations match. Notes carry the reading guide for each diagram.
